# 五项安全逻辑修复：实现、验证与使用变化

本版落实复审中的 F1—F5。没有修改 WiFi 凭据、硬件引脚、PID 默认增益、上位机二进制协议或关闭的视觉算法；没有自动烧录、启动电机、提交或推送 Git。

## 修复结果

| 问题 | 现在的实现 |
| --- | --- |
| F1 滤波越界被改成零点 | 正负越界及 NaN/Inf 都锁存 FILTER 故障；报告值保留为同方向阈值，不再变成正常零点；禁止再次启动，复位清除 |
| F3 日志拥堵丢 STOP | 语法、ID、数值合法的 `SET run 0` 在日志空间门限之前执行；队列满可丢应答，不丢停止动作 |
| F2 停机依赖 CPU0 控制 ISR | 新增 CPU1 的 CCU61_CH0 1ms 输出 ISR；CPU0 只发布完成计算，CPU1 统一操作 PWM 和运行期飞轮 TX，独立撤销输出 |
| F4 PWM 换向缺少真实零窗口 | 将 PWM 引脚暂切 GPIO 强制低；至少等一个 PWM 周期，再改 DIR；等方向建立时间及一个 PWM 周期后才恢复 ATOM 输出，全程无阻塞延时 |
| F5 飞轮反馈无有效期 | 仅完整且校验成功的速度帧刷新时间；启动前要求新鲜反馈，运行中超过100ms锁存故障并停止；损坏或半帧不续期 |

## 双核职责变化

```text
CPU0 CCU60_CH0，每1ms：
  IMU/反馈/滤波 → PID → 保护 → 发布完整的左右飞轮和行进指令

CPU1 CCU61_CH0，每1ms：
  读取稳定指令 → 检查停止代次、故障、完成计算时效、反馈时效
  → 应用行进PWM换向状态机 → 非阻塞写飞轮命令 → 周期请求测速
```

CPU0、CPU1 主循环继续分别处理 WiFi/诊断和按键/遥测。新增输出定时器使用独立的 CCU61 模块，服务 CPU1、优先级32；原控制 CCU60_CH0 仍服务 CPU0、优先级30。两核继续共享既有中断表。

`safety_output.c/.h` 是新增输出模块。运行时只有该 CPU1 ISR 操作 PWM 与飞轮 TX；初始化阶段仍由 CPU1 设置电机初值、发送零指令及首次测速。控制 ISR 不再轮询发送 UART，降低了控制与输出互相卡住的风险。

## 输出快照与停止协议

CPU0 用奇偶序列号及 DSYNC 发布左右指令、行进指令、完成时间和停止代次。CPU1 只接受前后序列号一致的完整快照；发布过程中卡住，不会更新已完成时间。

监测的是“整个计算已完成”的 STM 时间，不能仅在控制 ISR 开头加 `system_count` 来冒充计算完成。运行中超过10ms没有完整新指令，CPU1 将 PWM 强制低并发送飞轮零命令。

停止请求通过硬件 CAS 原子递增代次，随后清运行标志。CPU1 每1ms都检查代次和运行状态，不依赖 CPU0 返回。旧快照和旧启动请求无法使用新代次重新输出。CPU0 恢复后再清 PID/斜坡状态；PID 状态仍只由 CPU0 修改，避免跨核同时复位。

在 CPU1 输出中断正常工作的前提下，普通停止在下一次输出 tick 撤销 PWM并提交飞轮零帧；串口发送还存在字节传输时间。CPU0 卡住时，同样由这个独立路径处理。故障锁存后不会因为反馈恢复或按 K1 自动解除。

## PWM 换向的四状态

1. OFF：引脚为 GPIO低，影子比较值为0。
2. WAIT_ZERO：强制低后等待至少一个17kHz周期（约58.8μs）。
3. WAIT_ENABLE：在引脚仍为低时改DIR、装载幅值，等待至少100μs及一个PWM周期。
4. ACTIVE：恢复引脚的 ATOM 复用；同方向只更新占空比。再次反向重新从WAIT_ZERO开始。

每次1ms输出tick推进一步，通常一次换向需要约两个输出tick；它不会在控制ISR中忙等。等待中若收到停止，立即保持GPIO低并回OFF；等待中再次改变方向也会重新等待，不会直接恢复旧方向输出。

`pwm_output_enable()` 在逐飞 PWM 驱动新增：先把对应端口输出锁存位写低，再改GPIO输出模式；恢复时使用原 ATOM 引脚映射。它绕开了 `pwm_set_duty()` 只写影子寄存器的问题，没有改变引脚或PWM频率。

## 飞轮 TX 与反馈

`uart_try_write_buffer()` 仅在16字节硬件FIFO能容纳整帧时一次写入，返回成功/忙，不等待、不部分写入。运行期帧使用独立的栈缓冲，避免多个调用复用旧发送数组。输出帧优先，20ms测速请求排在输出帧之后；本地FIFO持续5ms无法排入输出命令会锁存UART故障并禁用行进输出，之后继续尝试发送零帧。

速度接收保留原7字节协议，新加完整帧时间和奇偶序列号；只有 A5/02、校验正确的完整帧才能更新时间。控制读取左右速度时检查序列号，避免拿到半更新的一对速度。

启用 roll 或 yaw 控制时，K1 启动要求最近100ms内有有效速度回复。只启用行进控制时不强制依赖飞轮反馈。运行中反馈过期会停车并锁存；重新收到反馈后也需复位才能重新启动。

## 新配置与日志

所有新时限在 `code/config.h`：

| 配置 | 默认值 |
| --- | ---: |
| SAFETY_OUTPUT_PERIOD_MS | 1ms |
| CONTROL_HEARTBEAT_TIMEOUT_MS | 10ms |
| MOMENTUM_FEEDBACK_TIMEOUT_MS | 100ms |
| MOTOR_UART_TX_TIMEOUT_MS | 5ms |
| MOTOR_DIR_SETUP_US | 100μs |

`[BOOT]` 与 `[APP]` 新增 `fault`、`fb` 字段：`fb=1` 表示当前所需飞轮反馈新鲜；`fb=0` 时当前 roll/yaw 配置不允许启动。只启用行进控制时该条件视为满足。

故障是位掩码，可叠加：

| fault值 | 含义 |
| --- | --- |
| 0 | 无锁存故障，仍需满足IMU、预热、反馈等其他启动门槛 |
| 1 | 滤波越界或非有限值 |
| 2 | 完整控制计算超过10ms未更新 |
| 4 | 飞轮有效反馈过期 |
| 8 | 飞轮UART TX持续忙超时 |
| 16 | 非有限/越界输出指令 |

这些新增故障只能整板复位清除。普通倾倒/按键停止沿用原有停止与重新按K1流程，但仍需满足全部启动条件。不要为启动而绕过 `fb` 或故障门槛；应检查实际串口引脚、供电和有效回复。

## 验收证据

- 六组真实C主机回归：默认、观察模式、仅飞轮、仅行进、方向取反、后台周期覆盖。
- 真实WiFi解析器测试日志积压249/2048字节仍停车，非法ID/数值/语法不能伪装停止；修正了测试辅助函数在队列满时写终止符越界的问题。
- 模拟CPU0完全停止、或只增长tick但不发布完成计算、或卡在奇数发布序列号；CPU1均可处理对应超时/停止。
- PWM模型区分影子值、已生效比较值和引脚强制低，校验DIR改变时PWM已禁用且零值已生效；覆盖停止与反向等待。
- 使用真实无刷协议代码验证有符号收发、错误校验不刷新时间、反馈过期、断流后不自动重启。
- 编译实际SDK新增适配函数的原始函数体，用FIFO/端口寄存器桩验证整帧容量和先写低后切GPIO的顺序。
- 参数回读、228字节数据与上位机解码、MCAM/CRC等原协议回归继续通过。

本机模拟不代表实测波形或实车直立。独立CPU1中断也不能覆盖整片芯片停机、掉电、外设硬件损坏或飞轮通信线物理断开后驱动器仍保持旧输出的所有情况；后者需要驱动侧失联保护或硬件禁能。此次没有修改/烧录无刷驱动板固件，不承诺其内部存在自动失联停机。

输出增加了跨核发布/应用的调度延迟，换向加入低电平窗口；PID默认值未改，但仍需架空或受控上板检查方向、波形、停机与实际响应。此前无UDP/无法启动的真实根因仍需诊断日志确认，不能因这五项修复就宣称其已在实车消失。
