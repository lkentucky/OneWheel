# DeepSeek WiFi 诊断补丁审查

审查对象是当前工作树及 `build_validation/patch_wifi_probe.py` 对应修改，基线取上次启动同步版本，不以旧 Git 提交代表当前源码。没有上板读取程序校验值，所以只能确认本机源码和固件产物，不能确认板上实际执行的版本。

## 已确认的合理部分

- 旧遥测发布与按键扫描依赖 `system_count`；该计数来自 1ms 控制回调。tick 不推进时，旧路径可能一直不发布 CPU1 遥测快照。
- CPU0 的 WiFi 状态机使用 STM 时间，网络日志与 CPU1 遥测快照不是同一条发送门槛。仅凭遥测 tick 依赖不能解释此前“日志和数据都没有”的全部现象。
- 增加 WiFi 可见的启动阶段、CPU1 tick 增量日志和有限 IMU 重试，有助于缩小定位范围。
- 原诊断版报告中的 168 个目标、ROM 90024 B、RAM 100668 B 与留存的 ADS 构建结果相符；原 HEX 为 216953 B，SHA256 为 `3def67c2f35b74a920e91039693064a1904301fba13808dc3a5a58a22a840289`。与上次启动同步版本相比 RAM 没变，约 26KB 的历史下降不能算本轮诊断补丁效果。

## 发现并补足的问题

1. **初始化失败仍在 1ms ISR 访问 IMU。** 驱动在设备 ID 自检失败时提前返回，后续量程、采样率等配置未执行。读取结果不能称为有效原始传感器数据；底层 SPI 的轮询等待也没有超时，额外增加故障路径中的阻塞风险。已恢复“就绪后采样”，保留 `imu=0` 状态与独立遥测，不取消电机保护。此处不意味着任意 IMU 拔线都必然让 SPI 阻塞。
2. **周期配置失效。** 直接删除限速让 `APP_TELEMETRY_PERIOD_MS` 不再生效；按键驱动仍拿 `APP_KEY_SCAN_PERIOD_MS` 换算按压阈值，但实际调用跟随主循环。已改用 STM 硬件时间分别调度，恢复两个宏的作用。
3. **按循环次数计“1 秒”不准确。** 已用 `APP_STATUS_LOG_PERIOD_MS` 替代 `APP_STATUS_LOG_LOOPS`，增加 `dms` 对照实际时间，tick 在每条日志中只采一次快照。
4. **测试未同步。** 首次独立运行原测试在 `wifi_link_log` 缺少模拟实现处失败。已补齐模拟接口，增加 tick 停止、配置不同周期、STM 低 32 位回绕、IMU 重试恢复和失败后禁采样回归场景。

## 对原报告的结论修正

- tick 停止、IMU 初始化失败是待检验的上游状态，不能据源码分支就认定为此次故障的实车根因。
- 阶段 5 表示进入 IMU 初始化/重试/首次采样，不等于自检失败。失败正常返回会继续到阶段 9，并报告 `imu=0`。
- 阶段 9 表示 PIT 初始化已经返回；只有 CPU1 状态日志持续更新，才能进一步说明 CPU1 主循环在推进。
- `dtick=0` 持续出现要查 ISR 未触发、ISR 阻塞或中断屏蔽等，不应直接认定换核能修复。当前服务配置与中断向量均匹配 CPU0。
- CPU0 持续发出 `[BOOT]` 时，不能再用阶段 1 推断“CPU0 没起来”。
- WiFi 日志要求网络链路成功，CPU1 数据帧还要求初始化返回后进入主循环；不承诺复位 1 秒内必有日志或数据。
- 按键扫描独立于 tick，不代表 tick 停止时电机仍能启动。预热、IMU、停止请求及控制中断的条件仍然有效。
