本次检查当前工作树，重点覆盖双核启动/停止、完成计算心跳、输出所有权、PWM 换向、飞轮反馈及 IMU 运行期检查。只审查并编写隔离复现，没有修改生产源码、配置或 Debug 固件，没有烧录或提交 Git。下列问题目前均未修复，上一版 HEX 仍包含这些逻辑。

## R1：跨核时间采样顺序会把新数据判成超时（P1）

位置：`code/safety_output.c:98-125`、`:54-57`，`code/small_driver_uart_control.c:8-13`。

输出 ISR 先在第100行记录 `now`，随后读取 CPU0 的完整命令。若 CPU0 恰在这两步之间发布完成时间更晚的新命令，第118行计算 `uint32(now - command.ticks)` 会下溢成极大值。例如先采时间1000，随后读到时间1001的新指令，差值是4294967295，触发 CONTROL_TIMEOUT，锁存 `fault=2` 并停止。

反馈检查有同类问题：`safety_output_feedback_ok()` 先采 STM 再调用 freshness 函数，CPU0 的 UART RX 可以在两者之间刷新 `feedback_ticks`，导致刚到的合法回复被当成过期，运行时锁存 `fault=4`。此问题也可能使启动检查偶发拒绝，但日志 `fb=0` 本身不证明串口失效。

隔离复现仅修改主机桩调度，在读时钟之后插入另一核的一次真实发布/真实 RX；生产函数不修改。两条路径都只相差1μs，均复现误停。原来的单线程顺序回归没有覆盖这种交错。

修复方向：先获取稳定的共享快照，再采当前时间计算年龄；反馈的时间、有效位与数据发布关系也应按一致快照处理。不要简单扩大超时，也不要对所有大差值一律视为新鲜，否则会掩盖真实过期。

## R2：过期反馈在 STM 低32位转完一圈后重新有效（P2）

位置：`code/small_driver_uart_control.c:8-13`、`:89-98`；启动入口 `code/posture_control.c:81-90`。

`feedback_valid` 一旦置1，只有重新初始化才清除；运行期只用32位时间戳相减判断年龄。停车待启动期间若反馈断流，检查先返回过期，但完整经过一个低32位周期后，同一个旧时间戳又落进100ms窗口。此时没有新 RX，也可通过 K1 的反馈门槛。

隔离复现：合法速度帧一次 → 等待超过100ms确认过期 → 不接收任何新字节，将时间推进到完整一圈后相同低字 → 发布新的控制计算 → `control_request_start()` 返回1。复现中的当前时间仍大于最后采样时间1μs，区别于 R1 的负年龄。

周期是 `2^32 / STM频率`，例如100MHz时约42.95秒；实际频率需读板上时钟。这不是普通相邻采样跨零失效：原有跨零测试通过，遗漏的是“最后一次有效反馈已经老了一整圈”。运行中已经锁存过的故障不会被这个问题清除，受影响的是尚未锁存的停车/待启动状态。

修复方向：使用足够长的一致时间基准，或由持续运行的监测者在观察到过期时可靠地使该接收代次永久失效，只有真正新帧才能恢复有效。处理清失效与 RX 更新的并发，不能让过期检查清掉刚到的新帧。

## R3：IMU 初始化成功后缺少运行期失效检测（P1，既有缺口）

位置：`code/app.c:115-128`、`code/posture_control.c:19-36`、`:147-156`；SDK `imu660rb_get_acc()` / `imu660rb_get_gyro()` 不返回本次采样成功状态。

`app_imu_ready` 只代表启动时初始化成功。运行中持续读取六轴数据，没有芯片状态、数据就绪时效或全零等异常帧判据。新加的“完整控制计算心跳”证明代码走完，不能证明 IMU 数据有效；滤波越界保护也覆盖不了仍落在正常范围内的错误数据。

隔离复现：正常初始化/预热并启动，随后让六轴原始寄存器连续200ms返回全零，飞轮反馈继续正常；实际控制代码仍 `run=1 / imu_ready=1 / fault=0`。这是软件对特定异常读数的处理结果，不是断言实际断线一定返回全零。SPI 真正卡住的情形则会由完整控制心跳超时处理，是另一条路径。

修复方向：补运行期 IMU 健康判据及相应停止策略，兼顾真实更新率；当前加速度/陀螺仪更新频率低于1kHz，不可将相邻数值相同或每1ms没有新数据简单认定为故障。

## 无刷驱动资料中的条件问题（不是已确认上板固件）

参考文件：`CYT2BL3_Brushless_Driver_Project-master/Seekfree_CYT2BL3_Double_Foc_Project/project/code/motor_driver_uart_control.c`。无法由本机源码证明驱动板当前烧录的就是此版本。

### D1：批量解析的校验和没有逐帧清零

第301行只在函数入口清 `check_data`，第358-387行循环处理多个候选帧时持续累加。隔离测试提取实际 `motor_driver_control_loop()` 函数体，替换 FIFO 和命令执行外围：同一 FIFO 中放合法非零命令及合法零命令，前者执行，后者因累计校验失败被丢。

触发需要一次 loop 调用处理多个候选帧。当前参考 RX 回调每读一个字节就调用一次 loop，因此不能声称每次连续收包都会触发；这是批量积压/重同步场景的缺陷。若采用相同固件，需要每个候选帧开始前清校验和。

### D2：二进制中的0x0A被当成ASCII换行

第537-544行对所有收到的 `\n` 增加字符串待处理计数，第307-345行又优先走字符串解析，未先辨别当前是否在二进制帧中。合法二进制占空比10的低字节就是0x0A。

隔离测试直接运行提取的实际 RX 回调和实际 loop，输入 `A5 01 00 0A 00 00 B0`，帧被丢弃，旧占空比保持。该问题也可能由二进制校验字节等于0x0A触发。修复应按帧协议分流，避免将二进制载荷中的换行识别成字符串命令。

这些复现只证明参考驱动源码的解析问题，不能直接归因当前小车的失联，也不代表已修好驱动或已在驱动板验证。

## 已检查但不列为新增故障

- 普通 STOP 已越过日志队列空间门限，满队列停车回归通过。
- CPU0 中断停住、发布卡在奇数序列号、仅增加tick不发布计算等原有超时回归通过；不因此保证整片芯片停机也能停电机。
- PWM 强制 GPIO低、换向等待和等待期收到 STOP 的原有模型回归通过。
- DeepSeek 提议在 `safety_output_can_start()` 中要求 `run_flag` 为1，此建议不采纳：调用方本来就在停车状态申请启动，加入这个条件会让所有正常启动失败。启动入口已检查停止代次及 pending 状态，不能仅凭该 helper 单独返回1就证明系统能越过完整启动流程。
- DeepSeek 提到 STOP 与一次硬件写之间仍有交错窗口；当前目标是下一次独立输出 tick 内撤销输出，不是跨核瞬时原子停止。没有足够证据将这个有限窗口另列成新缺陷。
- 关闭的摄像头算法中，上一轮记录的 Otsu 边界、丢信标除零/NaN、图像源不一致及检测状态缺失问题未修复；当前 `APP_CAMERA_ENABLE=0` 且主循环调用注释，未走该路径。
- 原有遥测仍不保证全部控制字段来自同一个 CPU0 控制周期，持续收到 UDP 也不能证明控制/IMU 健康；应结合 tick、fault、fb 和采样状态判断。
