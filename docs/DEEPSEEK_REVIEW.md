# DeepSeek 交付审查与修复

审查日期：2026-10-21。依据导出的 `session.v4.jsonl` 中人类用户要求、实际提交 `a327738`、
当前源代码、逐飞驱动及 McarPVC 上位机源码核对。结论：首版 IPS200 发布完成；
WiFi 移植有可用的协议和集成基础，但其原交付不足以满足“适配当前上位机、不过分阻塞主循环”的完整要求。
本次已修复下列本机可验证的问题，尚未做板卡和无线模块实测。

## 已完成的原任务

- GitHub 首版：重新通过 GitHub API 读取远端 master 和完整文件树，确认仍为
  `68bea6de95a833db544d30412f4b384d153eb732`，662 个文件的 blob SHA 与本地首版提交完全一致。
  它包含 IPS200 适配、README、ignore；不是只有本地提交。
- WiFi 基础集成：CPU0 有服务入口，CPU1 发布图像和遥测，控制中断有目标/死区/编码器接口，
  MUDP 和 MCAM 基本格式正确。原 ADS 构建确实通过，但不能据此确认状态机实时性和调参兼容性。
- Qcar 对比的 WiFi 结论应采用 DeepSeek 后续更正：Qcar 有图传分支，但 `wifi_spi_flag=1`
  的菜单赋值被注释，正常菜单流程不会启动图传。本次也已在源码核对。

## 发现和修复

| 问题 | 原实现的实际影响 | 当前处理 |
| --- | --- | --- |
| 运行态仍调用阻塞驱动 | INT 检查一次不能防止后续 wait_idle、发送/接收排空循环阻塞；一个 service 也可能进行多次事务 | 新增 wifi_link_io.c，发送/排空/flush/ACK 分步执行，RUN 每次最多一次 CS；250 ms 忙/事务超时后退避重连 |
| 接收优先级可能饿死发送 | 慢模块每次接收都超过 5 ms 时，下次又优先接收 | 接收周期从完成时间重新计时，给日志、数据和图像留出执行机会 |
| 调参接受非有限数 | strtod 的 NaN 可绕过普通大小比较；run 非零判断还可能误触发 | 完整检查转换、范围、尾随字符；拒绝 NaN/Inf；超长/控制字符命令整行丢弃 |
| host 在解析中直接连接 | 命令回调触发阻塞 socket 配置 | 校验 IPv4，先发送原目标的 ACK，再由 SOCKET 状态重连 |
| 上位机参数集合不匹配 | 原麦轮 GUI 的 GET ALL 一直提示不完整，独轮 PID 不在编辑表 | 增加 tools/monitor_onewheel.py，复用现有 GUI 源码的同时装入 32 项独轮参数；方案和设置独立保存；拒绝空 DONE 假成功 |
| 假定编码器单位等于 cm/s | 未知轮周长/编码器比例却回报物理速度 | 使用原生 speed（计数/20 ms）；cm/s 必须设置实测标定系数，否则该别名拒绝写入 |
| 斜坡回读不真实 | 默认 ramp_ms=500，但实际每 ms 只增加 0.03，到 160 约需 5333 ms | 默认回读改为 160/0.03；参数定义和转换统一，范围 100～20000 ms |
| 姿态与角速度单位混用 | 原互补滤波值是原始计数，却当作度；固定 10 ms 积分忽略图像/显示耗时；内环 PWM 当角速度 | 倾角由加速度计算；yaw 按实际 ms 间隔积分；转向目标使用外环给内环的原始角速度目标并按 IMU 比例换算 |
| 相机状态统计不准 | 每循环计帧；beacon.status 没有正常置 FOUND | 观察摄像头新帧标志计数；按检测候选有效条件报告事件 |
| PWM 遥测不等于实际指令 | 在停车判断/正反向 400 补偿前记录输入 | 记录实际下发指令，停车/关闭输出时为 0 |
| 跨核发布缺少顺序约束 | CPU0 可能读到 CPU1 混合快照或未完成图像/日志 | 添加 volatile、DSYNC、遥测序列号和 CPU1 就绪门控；PID、k1/k2 与中断共享变量显式可见 |
| 发送失败仍消耗数据 | 日志丢失、图像片号继续前进；CRC 反复计算 | ACK 后才出队/推进；失败保留日志，图像重发；每帧 CRC 缓存一次 |
| 可通过网络直接发车 | 参数接口把任意非零 run 写入运行标志 | 仅支持网络 run=0 停车，非零拒绝；不改变原车上电运行默认值 |
| 日志与验证说明夸大 | printf 没有全部接入；25 项测试未执行固件的实际 C 状态机 | 接入原 CSV 调试输出并纠正文档；新增直接执行实际 C 的主机验证 |

INIT 和 SOCKET 仍使用逐飞原驱动，可能阻塞 CPU0 主循环。RUN 的底层单次 SPI 传输也仍为同步轮询。
因此没有将整个链路标为完全非阻塞。CPU0 的控制中断可抢占主循环，实际中断抖动仍需示波器/时间戳实测。
