# 无 UDP 且 K1 无响应：启动诊断

> **最新版：** 输出与保护已升级，见 [SAFETY_FIXES_20261022.md](SAFETY_FIXES_20261022.md)。`[BOOT]`/`[APP]` 新增 `fault` 与 `fb`；故障位1/2/4/8/16分别表示滤波、控制超时、反馈过期、串口忙、指令异常。新增故障需整板复位清除；飞轮反馈不新鲜会拒绝启动。阶段8现在启动控制与独立输出两个1ms PIT。

本版针对 PWM+DIR 改动后出现的“上位机无原始 UDP 包、K1 无响应”增加启动定位信息，并修复 CPU1 未等待 CPU0 初始化延时系统的时序缺口。该缺口由源码确认；是否就是此次实车故障的原因，仍需烧录观察。

## 本次改动

- CPU0 完成时钟、STM 延时服务、调试串口和通信共享区初始化后，才允许 CPU1 初始化外设。
- UART0 输出固件编译时间、CPU1 初始化阶段和每秒运行状态；WiFi 初始化及 UDP 建连过程也输出到 UART0。
- `[BOOT]` 状态同步进入 WiFi 日志，但电脑只有在模块连网、UDP 建连及传输成功后才能看到；不保证复位后 1 秒内出现。
- 按键、遥测及 CPU1 状态日志按 STM 硬件时间分别调度，独立于 `system_count`。控制 PIT 不运行时仍可诊断，但不允许绕过启动保护。
- IMU 初始化最多重试 3 次；初始化失败后不在控制中断中继续采样，`imu=0` 表示 IMU 数据无效。
- 保持 PWM+DIR（P21.5 PWM、P21.4 DIR）、无刷 UART3、WiFi 私有配置及上位机协议不变。上电仍保持停止，K1 请求启动控制。

## 查看串口

使用 UART0：TX=P14.0、RX=P14.1，115200、8N1。电脑已识别过 Infineon JDS COM28；端口号以设备管理器当前结果为准，且需确认板载串口确实接 UART0。外接 USB 转串口时连接共地和正确的 3.3V 串口信号。

先打开串口，再复位。典型输出：

```text
[BOOT] OneWheel PWM_DIR Oct 21 2026 ... CPU0 ready
[BOOT] c0_polls=... c1_stage=9 tick=... imu=1 run=0 wifi=0
[NET] module init begin
[NET] module ... mac ...
[NET] UDP socket begin
[NET] udp ... local ... ip ...
[APP] st=9 tick=... dtick=... dms=... imu=1 run=0
```

`__DATE__`、`__TIME__` 由实际编译填写。网络初始化存在阻塞调用，因此初始化期间每秒状态行可能暂停。

| 字段 | 含义 |
| --- | --- |
| c0_polls | CPU0 主循环次数；持续增长表示 CPU0 在循环 |
| c1_stage | CPU1 已进入的初始化阶段，见下表 |
| tick | 1ms 控制定时中断计数；初始化结束后应增长 |
| imu | 1 为 IMU 初始化成功；0 时禁止 K1 启动 |
| run | 0 停止、1 控制运行；正常上电为 0 |
| wifi | 通信状态机已完成 UDP 建连为 1；不能单凭它证明电脑收到数据 |
| dtick | 两次 CPU1 状态日志之间的控制 tick 增量；此字段只在 `[APP]` 行中 |
| dms | 同一区间经过的 STM 毫秒数，用来对照 tick 是否正常推进 |

| c1_stage | 进入的步骤 |
| --- | --- |
| 1 | 等待 CPU0 初始化完成 |
| 2 | 中间电机 PWM+DIR 与编码器初始化 |
| 3 | 无刷驱动串口初始化 |
| 4 | 控制参数初始化 |
| 5 | IMU 初始化及首次采样 |
| 6 | 按键初始化 |
| 7 | 可选外设初始化（当前视觉等默认关闭） |
| 8 | 启动 1ms PIT |
| 9 | PIT 初始化返回，随后进入应用主循环 |

## 根据输出定位

- 完全没有启动行：先核对实际烧录文件、复位后是否执行、串口接线和端口；此时不能直接归咎于 WiFi。
- 阶段长期停在 2/3/5/7/8：检查该阶段初始化是否卡住；阶段表示“已进入”，不表示完成。
- 阶段 5 表示正在执行 IMU 初始化、重试或首次采样，不能直接认定“自检失败”；失败正常返回后仍会走到阶段 9，显示 `imu=0`。
- 阶段为 9，但 tick 不增长：检查定时器配置、ISR 是否进入或卡住，以及中断是否被长期屏蔽。CPU1 连续产生 `[APP]` 行可以进一步确认其主循环活着。当前中断向量和服务配置均指向 CPU0，不应在无证据时直接换核。
- `[BOOT]` 行仍出现且阶段长期为 1：CPU0 至少在执行诊断循环，应检查 CPU1 的共享就绪标志可见性与交接；不能说“CPU0 没起来”。
- `[NET] module init begin` 后没有结果：重点定位 WiFiSPI 模块初始化、SPI/握手与模块供电。
- `module init failed` 或连接重试：按失败步骤排查模块、热点连接或建连参数。
- 已显示 UDP 建连成功而电脑无包：再检查主机 IP、电脑监听、网络隔离与防火墙。
- `imu=0`：K1 被保护逻辑拒绝；不能通过取消保护来掩盖初始化故障。
- `imu=1` 且 tick 正常、按 K1 仍未启动：还要检查驱动开关、预热、待处理停止请求和保护。`[APP] start refused` 只表示启动请求被拒绝，不能单凭它确定某一原因。

诊断开关在 `code/config.h`：`APP_BOOT_DIAGNOSTICS_ENABLE`，默认 1。CPU0 状态周期 `APP_BOOT_DIAGNOSTICS_PERIOD_MS`、CPU1 状态周期 `APP_STATUS_LOG_PERIOD_MS` 均默认 1000ms；按键与遥测周期分别由 `APP_KEY_SCAN_PERIOD_MS`、`APP_TELEMETRY_PERIOD_MS` 控制。主循环工作量会增加调度延迟，因此这些是最小间隔，不是严格实时保证。定位完成后可关闭诊断。

本机模拟测试和 ADS 编译不能替代板上运行验证。本轮没有自动烧录，也没有触发电机启动。
